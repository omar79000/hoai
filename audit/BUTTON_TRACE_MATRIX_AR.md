تاريخ التحديث: 2026-11-18
الفرع: `reverse-engineering/initial-audit`

## معيار الإثبات

- **موثق بالدليل**: يصف دليل المستخدم الحقول أو النتيجة التي تظهر للمستخدم.
- **مؤشر ساكن**: اسم حقل أو مكتبة أو تقنية ظهرت داخل الملف التنفيذي، دون إثبات مسار التنفيذ.
- **غير مكشوف**: لا توجد لدينا حاليًا دالة الحدث أو طلب الراوتر أو الرد الفعلي أو عملية الحفظ التي تربط هذه العناصر.
- لم يتم تشغيل البرنامجين أو إرسال أوامر إلى راوتر حقيقي.

## 7.1 تفصيل حقول الإدخال كما يصفها الدليل

هذه تفاصيل حقول واجهة التطبيقين بحسب دليل المستخدم المرفق. هي مدخلات واجهة مؤكدة من الدليل، وليست دليلًا على كيفية تحويلها إلى معاملات RouterOS.

### شاشة الباقات
- اسم الباقة إلزامي.
- وقت الاستخدام، حجم التنزيل، وصلاحية البطاقة من أول استخدام؛ ترك الحقل فارغًا يعني غير محدود بحسب الدليل.
- عدد المستخدمين المتزامنين.
- السعر مطلوب لغرض طباعة البطاقة، ولا يصف الدليل السعر كشرط لتطبيق حدود الباقة على الراوتر.
- التعديل يتم بعد تحديد باقة واحدة؛ اسم الباقة لا يقبل التعديل.
- الحذف يدعم تحديد عدة باقات باستخدام Ctrl أو Shift.
- زر التحديث يعيد تحميل جدول عرض الباقات؛ مصدر الجدول غير محسوم.

### إنشاء بطاقات User Manager
- اختيار عميل User Manager موجود مسبقًا في MikroTik، عند وجود أكثر من عميل.
- اختيار الباقة ونقطة البيع وقالب الطباعة.
- وضع إنشاء كمية: بادئة اسم المستخدم، عدد البطاقات، عدد الخانات/الأرقام، خيار توحيد اسم المستخدم وكلمة المرور، ونمط الأحرف (أرقام فقط/أرقام وحروف/حروف فقط).
- إذا اختيرت نقطة بيع، يملأ البرنامج بادئة المستخدم تلقائيًا وفق إعداد نقطة البيع.
- وضع بطاقة واحدة: إدخال اسم المستخدم وكلمة المرور يدويًا؛ يمكن توليد قيمة عشوائية بالنقر المزدوج على حقلي الدخول وفق الدليل.
- حقول الباقة تشمل الوقت والحجم والصلاحية والتزامن كما سبق. لا نعرف بعد هل يرسل البرنامج كل حقل كما هو أو يحوله إلى وحدات RouterOS مختلفة.

### البحث والطباعة
- قسم البطاقات المنشأة حديثًا: مرشحا تاريخ من/إلى، البحث باسم البطاقة، وفلترة حسب الباقة.
- يعرض إجمالي عدد البطاقات المعروضة وإجمالي السعر المفترض تحصيله.
- خيارات ما قبل الطباعة: حفظ ملف الطباعة بعد الإنشاء، فتح PDF بعد إنشائه، والحفظ في مجلد الطباعة المحدد.
- يذكر الدليل أن حالة الطباعة تتغير من «غير مطبوع» إلى «مطبوع» وأن لون البطاقة في جدول العرض يتغير. لا يحدد أين تحفظ هذه الحالة.
- قوالب الطباعة الثلاثة: مختصر، بيانات الدخول، مفصل؛ مع اسم الشبكة ورقم الدعم وخلفيات وخيارات إظهار بيانات البطاقة.

### إدارة بطاقات User Manager
- البحث باسم البطاقة.
- تحديد بطاقة واحدة أو عدة بطاقات ثم تجميدها أو إلغاء التجميد أو حذفها.
- عرض الصلاحية المتبقية يتم عند الطلب، ولا تظهر تلقائيًا لأسباب أداء مذكورة في الدليل.
- إعادة الشحن تبدأ من قائمة الزر الأيمن ثم اختيار باقة للشحن.
- لا يحدد الدليل هل التجميد يغيّر خاصية داخل User Manager أو يعطّل الحساب بطريقة أخرى.

### إنشاء بطاقات Hotspot
- اختيار نوع البطاقة: مفتوح، WhatsApp فقط، Facebook فقط.
- يتطلب تفعيل خيارات WhatsApp/Facebook تأكيدًا منفصلًا.
- اختيار Hotspot Profile منشأ مسبقًا على الراوتر.
- لا تستخدم هذه البطاقات باقات User Manager؛ يحدد المستخدم خصائص كل بطاقة عند كل عملية إنشاء.
- يمكن تصفير عدادات البطاقة لتبدو كأنها لم تستخدم بعد.
- لا يشرح الدليل ما هي قواعد Firewall/Walled Garden التي تنشأ لخيار WhatsApp/Facebook، ولا يثبت أي أمر بعينه.

### المستخدمون المتصلون
- زر التحديث يعرض المستخدمين الحاليين.
- الأعمدة الموصوفة: اسم البطاقة، الوقت المستهلك، التنزيل، التحميل، الوقت المتبقي، الحجم المتبقي، اسم الجهاز (اختياري بعد تفعيل الخيار والتحديث)، وعنوان الجهاز على الشبكة.
- عمليتا الطرد: طرد عادي، أو طرد مع طلب إدخال اسم المستخدم وكلمة المرور في المرة التالية.
- لا يحدد الدليل هل اسم الجهاز يأتي من DHCP lease أو Registration table أو مصدر آخر.

### المبيعات والجلسات
- تقرير المبيعات يفلتر حسب فترة التاريخ، الباقة/السعر، ونقطة البيع.
- تقرير الاستخدام يفلتر حسب فترة التاريخ، ويعرض مجموع وقت الاستخدام وإجمالي التنزيل، ثم تفاصيل الجلسات: من/إلى، الوقت المستهلك، التنزيل، التحميل، وعنوان الجهاز.
- تقرير Hotspot مماثل في الواجهة لتقرير User Manager بحسب الدليل.
- أسماء DataSet الظاهرة في EXE مثل `tableSales`, `tableSales_HS`, `tableSessions_sum` تتوافق مع وجود جداول عرض للتقارير، لكنها لا تكشف مصدر تعبئتها.

### إعدادات Hotspot Server
- اختيار Hotspot Server Profile الموجود مسبقًا.
- تغيير اسم/عنوان الموقع المرتبط بالـ Profile مع رسالة تحذير أن المستخدمين لن يستطيعوا الدخول إذا لم يعرفوا الاسم الجديد.
- يذكر الدليل زر إعادة تشغيل السيرفر أو الراوتر. لا نعرف أيهما ينفذ الزر فعليًا أو هل توجد مطالبة تأكيد إضافية.

## 8. ما كشفته الملفات التنفيذية فعليًا

- مراجع شبكية ظاهرة: `TcpClient`, `NetworkStream`, `WebRequest`, `HttpWebRequest`, `HttpWebResponse`, `FtpWebRequest`, `NetworkCredential`.
- أسماء تقارير/بيانات: `tableSales`, `tableSales_HS`, `tableSessions_sum`, `ReportDS`, `SupReportDS`, وحقول جلسات/مبيعات موضحة أعلاه.
- وجود هذه الأسماء لا يحدد الدوال المستدعية أو ما إذا كانت تخص MikroTik أو خدمة أخرى.
- لا توجد حتى الآن أوامر RouterOS نصية موثقة أو method bodies قابلة للتحليل من EXE الأساسيين.

## 10. ما يلزم لإكمال تتبع كل زر دون تخمين

نحتاج إلى مدخل برمجي قابل للقراءة ومصرح به: نسخة EXE غير مغلفة/غير محمية من مطور البرنامج، أو مشروع المصدر وملفات PDB، أو نسخة تشخيصية من المطور. عند توفرها، يجب تتبع كل حدث WinForms إلى الدالة، ثم بناء طلب RouterOS ومعاملاته، وتحليل الردود الناجحة والفاشلة والمهلات، ثم تتبع تحديث الواجهة والكتابة المحلية.

إذا لم تتوفر نسخة قابلة للقراءة، فالبديل المشروع هو رصد تشخيصي داخل بيئة اختبار معزولة وبراوتر تجريبي تملكه، مع تسجيل طلبات التطبيق وردود الراوتر وسلوك قاعدة البيانات. لا ينبغي تجربة ذلك على شبكة إنتاج أو بحساب إداري واسع الصلاحيات.

**الخلاصة:** هذه المصفوفة تغطي العمليات التي يشرحها الدليل وتحدد المدخلات المرئية والنتائج المتوقعة، لكنها لا تدعي معرفة أوامر الراوتر أو الردود أو مسارات الحفظ الداخلية التي لم تكشفها الملفات.

### 8.2 ما لم يثبت بعد

- لم نعرف بعد المضيف والمنفذ الفعليين اللذين يمرران إلى `TcpClient.Connect`.
- لم نعرف ما إذا كان مسار TCP هو MikroTik API أو خدمة أخرى.
- لم نستخرج أوامر RouterOS أو بروتوكول المصادقة أو صيغة الرد.
- لم نربط هذه الدوال بزر إنشاء البطاقات أو التجميد أو الطرد أو التقارير.
- لم نستخرج SQL الفعلي الذي يمرر إلى OleDb.
- لم تظهر نصوص RouterOS literals واضحة في الدوال التي فحصناها.

### 8.3 لماذا يلزم تتبع callers؟

دوال TCP التي ظهرت حتى الآن هي wrappers رفيعة تستدعي `Connect`, `GetStream` و`Close`؛ وهي تستقبل المضيف والمنفذ كوسائط ولا تحتوي بنفسها على قيمة ثابتة تكشف المنفذ. لذلك يجب تتبع الدوال التي تستدعي هذه wrappers إلى أعلى call graph، ثم ربطها بتهيئة النماذج والأحداث.

يجري الآن استخراج:
- reverse call graph حتى ثلاثة مستويات من دوال TCP/HTTP/OleDb.
- IL للدوال التي تستدعي wrappers، مع الثوابت العددية ومراجع الدوال.
- جرد أنواع WinForms وطرقها لتحديد النماذج والـ event handlers.
- مراجع `ldftn` وأسماء أحداث `add_*` إذا كانت موجودة.

### 8.4 حالة كل مجموعة عمليات

حتى تظهر سلسلة handler → caller → network request → response، تبقى أوامر عمليات إنشاء الباقات والبطاقات والتجميد وإعادة الشحن والطرد والتقارير **غير مكشوفة**. وجود TCP/OleDb في البرنامج لا يبرر إسناد أي استدعاء إلى زر بعينه.


## 9. كشف نموذج واجهة يحتوي اتصال TCP — 18 نوفمبر 2026

أثبت تشغيل dnlib رقم [44207699308](https://github.com/omar79000/hoai/actions/runs/44207699308) أن كل نسخة تحتوي Form مشتقًا من WinForms، عدد دواله 94، ويضم دوالًا تستدعي `TcpClient` مباشرة:

| الوظيفة | 16.02.2 | 16.02.3 |
|---|---|---|
| إنشاء TCP client | `06000B34` | `06000B45` |
| الاتصال بعنوان ومنفذ | `06000B35` | `06000B46` |
| جلب NetworkStream | `06000B36` | `06000B47` |
| التحقق من IP | `06000B2C` | `06000B3D` |

وتوجد داخل النموذج دوال تتعامل مع `RadioButton.Checked` و`CheckBox.Checked` و`Control.Text`، إضافة إلى BackgroundWorker وحقول واجهة من TextBox وButton وLabel وغيرها. هذا دليل على وجود اتصال TCP مرتبط بنموذج واجهة تفاعلي، لكنه لا يكفي لتسمية النموذج نافذة اتصال MikroTik بشكل قطعي.

**المعلوم:** الاتصال يستخدم host وport كوسيطين يمران إلى `TcpClient.Connect(string,int)`.

**غير المعلوم:** القيم التي تدخل إلى هذين الوسيطين، المنفذ الفعلي، بروتوكول الرسائل، المصادقة، أوامر RouterOS، وكيفية قراءة الرد.

لم ينجح reverse-call-graph حتى الآن في ربط هذه الدوال بأحداث الأزرار؛ تقرير `network-callers.txt` يحوي دوال API المباشرة لكن لا يحوي أسطر `DEPTH=`. كما أن ربط BackgroundWorker بالـ delegate الفعلي لم يُحسم. لذلك لا يجوز إسناد اتصال TCP إلى زر محدد بعد.

التحليل التالي يستخرج IL كاملًا ومنقحًا وحقول النموذج الشبكي ونماذج OleDb، مع تجزئة النصوص غير المعروفة وإخفاء النصوص الحساسة، للوصول إلى مواضع نقل البيانات بين عناصر الواجهة والاتصال.
