## 1. نتيجة حاسمة: dnlib قرأ الملفين

بعد إصلاح أخطاء أداة الفحص نفسها، نجح dnlib في تحميل EXE وقراءة Metadata وجداول الأنواع والدوال. هذه أول مرة نمتلك فيها MethodDef قابلة للفحص من الملفين التنفيذيين.

| المؤشر | HawaE 16.02.2 | HawaE 16.02.3 |
|---|---:|---:|
| Assembly version | 15.10.0.0 | 16.2.3.0 |
| CLR runtime | v4.0.30319 | v4.0.30319 |
| Types | 142 | 144 |
| Methods | 3,217 | 3,234 |
| Interesting method-call edges | 858 | 864 |
| Safe RouterOS command literals | 0 | 0 |
| Parse status | parsed | parsed |

هذا يعني أن metadata ليست غير قابلة للقراءة مطلقًا؛ بل dnlib استطاع تفسيرها رغم أن ILSpy وmonodis وdnfile تعثرت. لا يعني هذا أن كل أسماء الأصناف والدوال أصلية أو مفهومة.

### أ. TCP

ثبت وجود مسارين برمجيين على الأقل يستعملان:

`TcpClient → Connect(host, port) → GetStream()`

وتوجد استدعاءات إغلاق اتصال. هذا دليل على أن التطبيقين يحتويان كود TCP مباشر، ويعطينا نقطة انطلاق مهمة لتتبع الاتصال.

لكن حتى الآن:
- لم نستخرج قيمة المنفذ الممررة إلى Connect.
- لم نستخرج اسم المضيف أو مصدره.
- لم نربط المسارين بعملية زر محددة.
- لم نستخرج صيغة البيانات التي تُكتب إلى NetworkStream أو الرد الذي يُقرأ منه.
- لا يوجد حتى الآن أمر RouterOS نصي مثبت.

لذلك لا يجوز بعد القول إن كل استدعاء TcpClient هو اتصال MikroTik API، رغم أنه احتمال يستحق الفحص.

### ب. HTTP/FTP

ظهر مسار مستقل يستخدم WebRequest وNetworkCredential وFtpWebRequest وRequestStream وGetResponse. وجود خصائص FTP مثل KeepAlive وUseBinary يجعل وجود وظيفة FTP محتملًا بقوة. لا نعرف وجهتها أو علاقتها بالراوتر، ولا نخلطها مع مسار TCP.

### ج. قاعدة البيانات

ظهر مسار OleDb واضح: إنشاء OleDbConnection وOleDbCommand، وتنفيذ ExecuteReader وExecuteNonQuery وExecuteScalar، وتعبئة DataSet عبر DbDataAdapter.Fill.

هذا يثبت وجود تعامل برمجي مع قاعدة بيانات عبر OleDb. وبالاقتران مع ملف Data.mdb الموجود في الأرشيفين، تصبح صلة OleDb بقاعدة Access المحلية مرجحة، لكن لم نثبت بعد أي استعلام SQL أو جدول أو زر يكتب إليه.

## 3. حالة أسماء الكود والحماية

رغم نجاح قراءة Metadata، كثير من أسماء الأنواع والدوال في Method Map عبارة عن أسماء غير مقروءة/مموهة. هذا يتفق مع وجود Obfuscation للأسماء أو تحويلها. لكن dnlib استطاع قراءة أجسام الدوال ومراجع الاستدعاء، وهذا يفتح باب تحليل IL بدل التوقف عند فشل التفكيك التقليدي.

النتيجة لا تثبت أن كل الكود محمي أو أن هناك حاجة إلى تجاوز حماية. لم نحاول unpacking أو patching أو تجاوز ترخيص.

## 4. لماذا لم تظهر أوامر RouterOS بعد؟

المحلل الحالي وجد 858 و864 حافة استدعاء مهمة، لكنه لم يجد أي literal آمن يطابق صيغة أمر RouterOS في أجسام الدوال. توجد عدة احتمالات:
- الأوامر تُبنى من أجزاء نصية بدل literal واحد.
- النصوص مخزنة في موارد أو إعدادات ثم تُقرأ وقت التشغيل.
- الأوامر تمر عبر طبقة وسيطة أو مكتبة أخرى.
- مسار TCP ليس MikroTik API أصلًا.
- بعض النصوص قد تكون مخفية/مشفرة أو تُفك أثناء التنفيذ.

هذه احتمالات بحث وليست نتائج مثبتة.

## 5. المرحلة التالية التي بدأ إعدادها

أُضيف إلى أداة التحليل استخراج محدود لأجسام الدوال ذات الصلة بالشبكة والبيانات وربط أحداث WinForms، دون نشر النصوص العامة أو الأسرار:
- تعليمات IL داخل دوال TCP/HTTP/FTP/OleDb.
- مراجع الدوال التي تستدعيها تلك الدوال.
- الثوابت العددية التي قد تكشف المنفذ أو المهلة.
- نصوص أوامر RouterOS فقط إذا ظهرت بصيغة واضحة، مع تنقيح معاملات الأسرار.
- تعليمات `ldftn` وعمليات `add_Click` و`add_MouseClick` و`add_DoubleClick` لربط عناصر الواجهة بالدوال.

سيُستخدم ذلك لتحديد event handlers ثم تتبع سلسلة الزر → الدالة → الاتصال → الطلب/الرد → التخزين.

## 6. الحكم الحالي

- **مؤكد:** dnlib قرأ الملفين، ووجد 142/144 Type و3,217/3,234 Method.
- **مؤكد:** كلاهما يحتوي مساري TCP متشابهين واستدعاءات HTTP/FTP وOleDb.
- **مرجح:** هناك Obfuscation لأسماء الأنواع والدوال.
- **غير مثبت:** أن TCP هو MikroTik API، أو المنفذ المستخدم، أو صيغة API، أو أي أمر RouterOS.
- **غير مثبت:** أي زر بعينه يطابق هذه الدوال.
- **لم يتم:** تشغيل EXE أو الاتصال براوتر حقيقي.

النجاح هنا تقدم جوهري: انتقلنا من عدم القدرة على قراءة MethodDef إلى قراءة Metadata وأجسام الدوال ومراجع الاستدعاءات. لكن الوصول إلى أوامر RouterOS يتطلب تحليل IL الموجه وربط الأحداث، وليس الاكتفاء بعدد الدوال أو أسماء مكتبات الشبكة.
