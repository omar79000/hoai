## 3. الوظائف التي يثبتها دليل المستخدم

دليل المستخدم العربي الموجود مع حزمة 16.02.3 يصف الوظائف التالية:

### أ. الباقات

الباقة تجمع خمسة قيود:
1. وقت الاستخدام.
2. حجم التنزيل.
3. السرعة.
4. صلاحية الاستخدام ابتداءً من أول استخدام.
5. عدد المستخدمين المتزامنين للكرت.

ويدعم الدليل إضافة الباقات وتعديلها وحذفها، مع اشتراط اسم الباقة، وذكر أن السعر يستخدم في الطباعة.

### ب. بطاقات User Manager

- اختيار عميل User Manager من قائمة العملاء المعرفة مسبقًا على MikroTik.
- ربط البطاقة بباقة ونقطة بيع.
- إنشاء بطاقة واحدة أو مجموعة بطاقات.
- تحديد بادئة اسم المستخدم والكمية وعدد الأرقام.
- معاينة/عرض البطاقات وحالة الطباعة.
- تصدير/طباعة البطاقات إلى PDF، مع خيارات حفظ وفتح الملف بعد الإنشاء.
- تبويب يعرض جميع البطاقات مع البحث.
- تجميد البطاقة أو إعادة تفعيلها، وإعادة شحنها بباقة أخرى.
- ربط المبيعات بنقاط البيع والباقات.

### ج. بطاقات Hotspot

- إنشاء بطاقات مرتبطة بملف Hotspot Profile موجود على الراوتر.
- يصف الدليل أنماطًا: مفتوح، WhatsApp فقط، Facebook فقط.
- خصائص البطاقة تحدد عند الإنشاء بدل الاعتماد على باقات User Manager.
- توجد خيارات لتصفير عدادات البطاقة.
- تفاصيل آلية فرض وضع WhatsApp/Facebook لم تُثبت بعد من الشيفرة.

### د. المستخدمون المتصلون حاليًا

يعرض الدليل معلومات تشمل:
- اسم البطاقة.
- الوقت المستهلك.
- التنزيل والتحميل.
- الوقت والحجم المتبقيان.
- اسم الجهاز عند تفعيل الخيار.
- عنوان الجهاز على الشبكة.

كما يصف عمليتي طرد المستخدم، أو طرده مع طلب اسم المستخدم وكلمة المرور في الدخول التالي.

### هـ. تصميم وطباعة البطاقات

ثلاثة قوالب:
- مختصر.
- بيانات الدخول.
- مفصل.

وتشمل الخيارات خلفيات الصور، اسم الشبكة ورقم الدعم، إظهار/إخفاء العناوين، الرقم التسلسلي، الإطار وتقسيمات البطاقة، الخط وحجمه. يذكر الدليل أحجامًا ثابتة لبعض القوالب، وقالبًا مفصلًا بحجم 9×5 سم. وجود iTextSharp وملفات PDF يدعم وجود مسار توليد PDF، لكنه لا يحدد وحده كل تفاصيل الطباعة الداخلية.

### و. المبيعات وتقارير الاستخدام

- تقارير مبيعات User Manager وHotspot كلٌ على حدة.
- التصفية حسب التاريخ والباقة ونقطة البيع.
- تقرير استخدام حسب الفترة.
- تجميع الوقت والتحميل لكل بطاقة.
- تفاصيل الجلسات: البداية والنهاية والمدة والتنزيل والتحميل وعنوان الجهاز.
- ملفات Crystal Reports باسم `Sales.rpt` و`Sessions_sum.rpt`.

### ز. إعدادات الراوتر

الدليل يصف:
- اختيار Hotspot Server Profile.
- تغيير اسم/عنوان موقع تسجيل الدخول المرتبط بالملف المحدد، مع تحذير من أثره على وصول المشتركين.
- خيار إعادة تشغيل السيرفر أو الراوتر.

**تنبيه تشغيلي:** إعادة التشغيل وتغيير إعدادات Hotspot قد تؤثر على المشتركين؛ لن يتم تضمينهما في أي تطوير تلقائي أو اختبار حي دون موافقة صريحة وخطة رجوع.

## 4. بنية البيانات: ما نعرفه وما لا نعرفه

كل نسخة تحتوي قاعدة Access بحجم 565,248 bytes، لكن البصمتين مختلفتان:

- قاعدة نسخة 16.02.2: `4657df728b77eb7b306e99260e42a228227dfcb47762f741b4100f69e911550d`
- قاعدة نسخة 16.02.3: `99ea5f6fab96027d777fdf81e2928e24be579dc0ff2f37c8dd2e8d206ea992a2`

تظهر داخل EXE أسماء جداول/مجموعات بيانات مولدة:
- `tableSales`
- `tableSales_HS`
- `tableSessions_sum`

هذا دليل على وجود مجموعات بيانات تحمل هذه الأسماء، وليس تأكيدًا نهائيًا أن أسماء الجداول الفعلية داخل ملف MDB مطابقة لها. لم يتم بعد استخراج مخطط Access (أسماء الجداول والأعمدة والمفاتيح)؛ لذلك لا نستنتج العلاقات أو الحقول من أسماء المجموعات وحدها.

ملفات `Sales.rpt` و`Sessions_sum.rpt` متطابقة بايتًا بين الحزمتين وفق SHA-256. كما أن `itextsharp.dll` ودليل المستخدم متطابقان بايتًا بينهما.

## 5. المقارنة الأولية بين الإصدارين

1. النسختان تطبيقان من العائلة نفسها وبنية تشغيل متقاربة جدًا بحسب ملفات EXE والإعدادات والمكونات المشتركة.
2. الملف التنفيذي 16.02.3 أكبر بـ 48,128 bytes من 16.02.2؛ الحجم وحده لا يحدد الميزات المضافة.
3. قواعد البيانات مختلفة رغم تطابق الحجم؛ يلزم استخراج المخطط ومقارنة الجداول والحقول قبل تقرير التوافق أو الترحيل.
4. تقارير Crystal وiTextSharp ودليل المستخدم متطابقة.
5. حزمة 16.02.2 تحتوي `Newtonsoft.Json.dll` بينما لم تظهر هذه المكتبة ضمن ملفات حزمة 16.02.3 المستخرجة. لا نستنتج من ذلك وحده أن JSON أزيل من التطبيق؛ قد تكون الوظيفة تغيرت أو أصبحت مدمجة أو غير مستخدمة.

## 6. ما لم يثبت بعد

- لم نحدد بعد هل الاتصال الأساسي بالراوتر عبر RouterOS API أم HTTP أم sockets أو مزيج منها.
- لم نستخرج أو نثبت أوامر RouterOS ومساراتها ومعاملاتها وتسلسل تنفيذها.
- لم نحدد آلية إنشاء/تجميد/إعادة شحن المستخدمين على مستوى أوامر الراوتر.
- لم نستخرج مخطط جدولي Access أو محتويات قواعد البيانات.
- لم يتم تفكيك الشيفرة إلى مصدر قابل للمراجعة بعد. محاولة ILSpy الحالية توقفت عند أول ملف EXE برمز خروج 70؛ تم تعديل workflow حتى لا يؤدي تعثر ملف واحد إلى إيقاف بقية الفحص.
- لم يتم تشغيل التطبيقين أو اختبار توافقهما مع RouterOS.

## 7. الخطوة الهندسية التالية

1. إعادة تشغيل التحليل بعد إصلاح معالجة فشل ILSpy.
2. استخراج مخطط Access فقط دون نشر بيانات السجلات.
3. مراجعة metadata ومواضع استدعاء الشبكة في assemblies التي تسمح أدوات التحليل بقراءتها، دون تجاوز آليات الحماية أو الترخيص.
4. توثيق طبقة الاتصال وأوامر RouterOS فقط عندما يظهر دليل مباشر من call sites أو إعدادات موثوقة.
5. بناء مقارنة تفصيلية بين نسختي قاعدة البيانات والموارد والملفات.
6. بعد اكتمال الفهم، إعداد مشروع تطوير منفصل واختبارات محاكاة/مختبر، مع إبقاء النسختين الأصليتين دون تغيير.
