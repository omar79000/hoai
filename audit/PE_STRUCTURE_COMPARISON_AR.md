# التحليل البنيوي العميق لملفي HawaE 16.02.2 و16.02.3

تاريخ الفحص: 2026-11-18  
الفرع: `reverse-engineering/initial-audit`  
المصدر: تقارير PE/CLR الساكنة من تشغيل GitHub Actions رقم 44203435194. لم يتم تشغيل أي ملف تنفيذي.

## 1. خلاصة تنفيذية

- الملفان PE32 لمعمارية x86، ويدخلان عبر CLR بواسطة `mscoree.dll!_CorExeMain`.
- كلاهما يحتوي قسمًا أولًا باسم عشوائي/غير مقروء، يجمع صلاحيات الكتابة والتنفيذ، وانتروبيته 7.9999 تقريبًا.
- كلاهما يحتوي CLR Metadata Root بإصدار `v4.0.30319`، لكن تدفقات Metadata تتضمن أسماء مكررة وتدفقًا غير معتاد باسم `#Schema`.
- التخطيط البنيوي للملفين متشابه بدرجة كبيرة، مع اختلافات أحجام وإزاحات متناسبة مع اختلاف حجم EXE.
- النسخة 16.02.3 تحتوي Overlay بحجم 41,472 بايت؛ لم يسجل الفحص Overlay للنسخة 16.02.2.
- هذه القرائن تجعل وجود تغليف أو آلية حماية/تحميل غير تقليدية احتمالًا قويًا، لكنها لا تحدد اسم الحامي ولا تثبت آلية بعينها.

### تصحيح مهم بخصوص dnlib

أظهر سجل GitHub Actions أن dnlib لم يفشل في تحليل Metadata. مشروع أداة dnlib نفسه لم ينجح في التجميع بسبب خطأ C# في تعبير Regex داخل `Program.cs` (CS1012/CS1009/CS1010). تم تصحيح صياغة التعبير في الفرع وإضافة `tools/**` إلى مسارات تشغيل Workflow. لذلك لا يجوز استخدام تشغيل 44203435194 كدليل على فشل dnlib.

التشغيل الجديد بعد هذا الإصلاح هو الاختبار الفعلي الذي سيحدد هل dnlib يستطيع قراءة Metadata أم لا.

## 7. مؤشرات النصوص والمكتبات

ظهرت في النسختين مؤشرات متقاربة جدًا، منها:

- الشبكة: `TcpClient`, `System.Net.Sockets`, `NetworkStream`, `WebRequest`, `FtpWebRequest`, `HttpWebRequest`, `HttpWebResponse`.
- قاعدة البيانات: `OleDbCommand`, `OleDbConnection`, `OleDbDataReader`, `OleDbDataAdapter`, `DataSet`, `DataTable`.
- الواجهة: `Button`, `RadioButton`, `add_Click`, `add_MouseClick`, `add_DoubleClick`.
- بيانات وتقارير: `tableSales`, `tableSales_HS`, `tableSessions_sum`, `columnuser`, `columnprice`, `columntotal_time`, `columntotal_download`, `expiration_date`.

عدد السلاسل المصنفة في الفحص: 72 للنسخة 16.02.2 و70 للنسخة 16.02.3. الاختلافان الوحيدان في مجموعة النصوص المصنفة كانا اسمَي موردين عشوائيين من نوع `.resources` ظهرا في 16.02.2 فقط. هذه سلاسل ومراجع، وليست call sites ولا أوامر RouterOS.

## 8. الاستنتاجات المسموح بها

1. بنية الملفين متشابهة جدًا، بما في ذلك قسم أول عالي الانتروبية وخصائص RWX وتخطيط CLR metadata غير المعتاد. هذا يرجح وجود آلية تغليف/حماية مشتركة أو سلسلة بناء واحدة، ولا يثبت اسم الأداة أو نوعها.
2. النسخة 16.02.3 تضيف Overlay حجمه 41,472 بايت؛ سبب ذلك غير معروف حتى يتم تحليل محتواه.
3. كلا الملفين يحملان مؤشرات .NET وWinForms وOleDb وTCP/HTTP، لكن لا يمكن ربط أي منها بوظيفة محددة أو اتصال MikroTik حتى تُقرأ الدوال واستدعاءاتها.
4. لا يوجد حتى الآن أمر RouterOS فعلي مثبت لأي زر.
5. لا يوجد مبرر حالي لتجاوز حماية أو unpacking. الخطوة التالية هي تجربة dnlib بعد إصلاح أداة الفحص؛ إذا نجحت القراءة، ننتقل إلى أنواع النماذج وأحداث Click وcall graph والـ IL ذي الصلة. إذا فشلت مع خطأ metadata موثق، نحتاج نسخة source أو نسخة build غير محمية مصرح بها من المطور أو أدلة تشخيصية من بيئة اختبار يملكها المستخدم.
