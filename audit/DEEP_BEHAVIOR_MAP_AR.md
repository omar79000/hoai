## 2. ما نعرفه عن طبقات البرنامج

### الواجهة
الملفات التنفيذية تطبيقات Windows Forms/.NET Framework 4 وفق الفحص السابق. لم نستطع حتى الآن ربط عناصر الواجهة بأسماء event handlers لأن تفكيك EXE فشل.

### التخزين المحلي
يوجد ملف `Data.mdb` في كل أرشيف. البنية المستخرجة في النسختين تحتوي الجداول التالية:

- `Selling_points`: `sp_name`, `sp_prefix`, `sp_address`, `shown_in_web`, `sp_id`.
- `Settings`: `setting_id`, `setting_name`, `setting_value`, `category`.
- `graghics_presets`: `setting_id`, `setting_name`, `setting_value`, `preset_name`.

لم تُنشر قيم السجلات. لا توجد في المخطط المستخرج جداول واضحة بأسماء بطاقات أو مبيعات أو جلسات؛ لذلك لا يصح القول إن MDB هي قاعدة البيانات الرئيسية لبيانات المشتركين أو البطاقات. قد تكون بيانات تلك الوظائف على الراوتر أو في DataSet مؤقتة أو في مصدر آخر.

بصمتا ملف MDB مختلفتان بين الإصدارين رغم تطابق المخطط؛ لذا قد تختلف بيانات الإعدادات الفعلية، ولم نعرضها.

### التقارير والبيانات المؤقتة
ظهرت في EXE أسماء مثل:

- `tableSales`, `tableSales_HS`, `tableSessions_sum`.
- `columnuser`, `columnprice`, `columncurrency`, `columnselling_point`, `columncomment`.
- `columnfirst_login_date`, `columntotal_download`, `columntotal_time`.
- `start_date`, `expiration_date`, `licensing_server_date`, `expired`.

هذه مؤشرات إلى DataSet/حقول وتقارير محتملة، وليست إثباتًا على أسماء جداول MDB أو على طريقة استدعائها.

### الشبكة
وجدنا داخل EXE مؤشرات إلى:

- `TcpClient`, `System.Net.Sockets`, `NetworkStream`.
- `WebRequest`, `HttpWebRequest`, `HttpWebResponse`, `GetResponse`, `GetResponseStream`.
- `FtpWebRequest`, `NetworkCredential`, `ICredentials`.

كما أن ملفي `.exe.config` يحتويان إعداد `useUnsafeHeaderParsing=true` لطلبات HTTP.

هذا يثبت وجود مراجع/إعدادات تخص هذه التقنيات داخل التطبيق، لكنه لا يثبت أي تقنية منها مستخدمة للتخاطب مع RouterOS. وقد تكون بعض المراجع لخدمات أخرى أو تحديثات أو تراخيص أو تنزيل ملفات.

لم تظهر نصوص RouterOS/MikroTik أو أوامر API صريحة قابلة للقراءة في الفحص الحالي.

## 3. ما يصفه دليل المستخدم — وظائف ظاهرة وليست تفاصيل تنفيذ

يصف الدليل وظائف لإدارة User Manager وHotspot، من بينها:

- إنشاء بطاقة مفردة أو مجموعة بطاقات، وتحديد البادئة والكمية وعدد الأرقام.
- إعداد باقات تتضمن وقت الاستخدام، حجم التنزيل، السرعة، صلاحية تبدأ من أول استخدام، وعدد الجلسات المتزامنة.
- تجميد البطاقة وإعادة تفعيلها وإعادة شحنها.
- عرض المستخدمين المتصلين واستهلاك الوقت والتحميل والتنزيل، وعرض الجهاز/IP عند توفرهما، وطرد المستخدم.
- طباعة البطاقات إلى PDF باستخدام قوالب متعددة وخلفيات واسم الشبكة وبيانات الدعم.
- تقارير مبيعات User Manager وHotspot حسب التاريخ والباقة ونقطة البيع، وتقارير جلسات واستخدام.
- إعدادات Hotspot Server Profile وصفحة الدخول.

لا تكشف هذه الأوصاف وحدها الأوامر أو ترتيبها أو ما إذا كانت العملية تنفذ طلبًا واحدًا أو عدة طلبات.

## 4. نتيجة محاولة قراءة IL والـ metadata

التشغيل رقم 14 اكتمل بنجاح، لكن نتيجة `dnfile` كانت غير صالحة للتحليل الوظيفي: جداول `TypeDef`, `MethodDef`, `MemberRef` وغيرها ظهرت صفرًا، مع تحذيرات عن تكرار تدفقات `#GUID`, `#Strings`, `#Blob`، وتعذر قراءة `#Schema` وجداول .NET.

ظهر أيضًا تحذير PE عن قسم يجمع خصائص الكتابة والتنفيذ. هذه قرائن قد تتوافق مع ملف مضغوط/مغلف أو metadata غير قياسية، لكنها لا تحدد أداة الحماية ولا تثبتها. فشل ILSpy وmonodis السابق يدعم أن أدوات القراءة الحالية لا تستطيع تحليل EXE مباشرة.

تم إصلاح مصنف حالة المحلل كي لا يعتبر جداول metadata الفارغة نجاحًا في القراءة. وسيعاد اختبار ذلك في التشغيل التالي.

تم إنشاء ملف مستقل أكثر تفصيلًا يربط كل عملية بما يصفه دليل المستخدم من مدخلات ونتائج، ويضع علامة واضحة على أوامر الراوتر والردود والحفظ التي لا تزال غير مكشوفة:

[`audit/BUTTON_TRACE_MATRIX_AR.md`](BUTTON_TRACE_MATRIX_AR.md)

تم تحديث الدليل بناءً على حزمة التحليل رقم 15، التي نجحت في استخراج النص العربي لدليل المستخدم. وتؤكد تقارير `dotnet_probe` أن metadata للملفين التنفيذيين الأساسيين ما زالت غير قابلة للقراءة؛ نجاح workflow هنا نجاح لاستخراج التقارير وليس نجاح تفكيك البرنامج.

## 7. المسار التقني التالي

1. استخراج نص ملفات PDF المرفقة مع الأرشيفين وإضافتها إلى حزمة التحليل لتحديد تسلسل الشاشات والحقول وخيارات كل عملية.
2. إعادة تشغيل محلل metadata بعد تصحيح تصنيف `unreadable_metadata`.
3. فحص موارد WinForms وملفات `.resources` وملفات الإعدادات والـ manifests لاستخراج أسماء النماذج وعناصر الواجهة دون تشغيل EXE.
4. إذا بقيت metadata غير قابلة للقراءة، يلزم مصدر إضافي مشروع: نسخة غير محمية/غير مغلفة من المطور، أو ملفات PDB/source، أو تفريغ ذاكرة موثق من بيئة اختبار يملكها المستخدم. لن يتم تجاوز ترخيص أو حماية أو استخدام أساليب تخفي.
5. بعد تحديد الدوال، تتبع call graph لكل حدث زر، ثم توثيق الطلبات والردود وترتيبها، مع اختبار لاحق على راوتر تجريبي معزول وبصلاحيات محدودة، وليس على راوتر إنتاج.

## 8. معايير إعلان الفهم الكامل

لن نعلن أن زرًا مفهوم بالكامل إلا إذا توفرت أدلة تربط:
1. عنصر الواجهة بالحدث والدالة.
2. المدخلات والتحقق والتحويل.
3. كل طلب خارجي وأمر RouterOS ومعاملاته.
4. الردود الناجحة وأخطاء RouterOS والمهلات وإعادة الاتصال.
5. تحديث الواجهة ومصدر البيانات.
6. الكتابة إلى MDB أو ملف أو قاعدة أخرى، أو إثبات عدم وجود حفظ محلي.
7. سلوك الإصدارين إذا اختلف.

**الحالة الحالية:** أصبح لدينا توثيق أدق للمدخلات والنتائج التي يصفها دليل المستخدم، لكننا لم نصل بعد إلى تتبع زر واحد من الواجهة إلى أمر RouterOS ثم الرد والحفظ. لا توجد حاليًا أوامر RouterOS مثبتة لأي زر. إكمال ذلك يتطلب نسخة برمجية قابلة للقراءة ومصرحًا بها أو رصدًا تشخيصيًا داخل مختبر اختبار معزول.


## 9. التحليل البنيوي الأعمق للـ PE وCLR — تحديث 18 نوفمبر 2026

أُنجز فحص PE/CLR مفصل للملفين في التشغيل 44203435194. أهم النتائج:

- كلا الملفين PE32 x86 ويستوردان `mscoree.dll!_CorExeMain`.
- في كل ملف خمسة أقسام. القسم الأول اسمه غير مقروء، يجمع RWX، وانتروبيته 7.9999 تقريبًا، وحجمه الخام نحو 2.17 MB.
- يوجد قسم `.text` تقليدي نسبيًا، ثم `.rsrc` و`.reloc` وقسم أخير بلا اسم.
- كلاهما يعلن CLR Metadata version `v4.0.30319`، لكن تدفقات Metadata تتضمن تكرار `#GUID` و`#Strings` و`#Blob` وتدفق `#Schema` غير المعتاد.
- النسخة 16.02.3 تحتوي Overlay بحجم 41,472 بايت، بينما لم يظهر Overlay للنسخة 16.02.2.
- موارد PE التسعة في كل نسخة متقاربة جدًا في الأحجام، وكذلك مؤشرات النصوص ومراجع الشبكة وOleDb وWinForms.

هذه القرائن تجعل التغليف أو التحميل غير التقليدي احتمالًا قويًا، لكنها لا تحدد أداة الحماية ولا تثبتها. التفاصيل والأحجام والإزاحات والبصمات في [مقارنة بنية PE وCLR](PE_STRUCTURE_COMPARISON_AR.md).

### تصحيح سجل dnlib

سجل التشغيل 44203435194 كشف أن dnlib لم يصل أصلًا إلى قراءة الملفين؛ مشروع أداة التحليل نفسه لم يُبنَ بسبب أخطاء C# في Regex عند السطر 46 من `Program.cs`. تم إصلاح الخطأ في commit `6cc8ee4`، وأُضيف مسار `tools/**` إلى محفز Workflow في commit `f914970`. بدأ التشغيل 44204010260 على commit إصلاح Workflow، وما زال قيد التنفيذ عند آخر تحقق.

لذلك لا نصنف dnlib على أنه فشل في قراءة Metadata حتى تظهر نتيجة التشغيل المصحح. لم يتم تشغيل التطبيقين ولم يتم تجاوز حماية أو الاتصال براوتر.


## 10. نتيجة dnlib المصححة — 18 نوفمبر 2026

اكتمل تشغيل 44205495894، وهذه المرة قرأ dnlib Metadata للملفين بنجاح:
- 16.02.2: 142 Type و3,217 Method و858 حافة استدعاء مهمة.
- 16.02.3: 144 Type و3,234 Method و864 حافة استدعاء مهمة.

ظهرت في كل نسخة استدعاءات TCP عددها اثنان إلى `TcpClient.Connect(string,int)`، واستدعاءان إلى `GetStream()`، مع منشئي TcpClient وإغلاق الاتصال. كما ظهرت استدعاءات HTTP/FTP وOleDb. هذه أدلة على وجود هذه المسارات البرمجية، لكنها لا تثبت أن TCP يتصل براوتر MikroTik أو تكشف المنفذ أو الأوامر؛ لم يظهر أي literal آمن يطابق أمر RouterOS حتى الآن.

تقرير الأدلة التفصيلي: [DNLIB_PARSE_FINDINGS_AR.md](DNLIB_PARSE_FINDINGS_AR.md).

أضيف الآن استخراج IL موجهًا لأجسام دوال الشبكة والبيانات، وربطًا لأحداث WinForms عبر `ldftn` و`add_Click` ونظائرها. هذا هو المسار الذي يمكن أن يكشف معاملات Connect، والثوابت، وربط الزر بالدالة. لم يتم تشغيل EXE أو الاتصال براوتر.


## 11. اكتشاف نموذج اتصال TCP داخل واجهة WinForms — تشغيل 44207699308

نجح تشغيل dnlib المصحح في قراءة النسختين، ونُشر تقرير التحليل المنقح في Artifact رقم `14384686967` (تشغيل [44207699308](https://github.com/omar79000/hoai/actions/runs/44207699308)).

### 11.1 النموذج الذي يحتوي مسار TCP

في النسختين توجد فئة مشتقة مباشرة من `System.Windows.Forms.Form` تحتوي 94 Method، وبداخلها دوال مساعدة تستدعي TCP مباشرة:

| العنصر | 16.02.2 | 16.02.3 |
|---|---|---|
| فئة Form المرشحة | `x(<:sj+vsyy%4%z8,mrzCzs*` | `B3WbO\\q:tt44BYB;;|iWh5`[%` |
| عدد الدوال | 94 | 94 |
| إنشاء TcpClient | Token `06000B34` | Token `06000B45` |
| Connect(host, port) | Token `06000B35` | Token `06000B46` |
| GetStream() | Token `06000B36` | Token `06000B47` |
| IPAddress.TryParse | Token `06000B2C` | Token `06000B3D` |
| RadioButton.Checked helper | Token `06000B38` | Token `06000B49` |
| Control.Text helper | Token `06000B39` | Token `06000B4A` |
| CheckBox.Checked helper | Token `06000B43` | Token `06000B54` |

هذه ليست مجرد مراجع مكتبة: جسم الدالة الخاصة بــ Connect ينفذ `TcpClient.Connect(string,int)`، والدالة الخاصة بــ GetStream تنفذ `TcpClient.GetStream()`. الوسيطان host وport يمران إلى wrapper، ولا توجد قيمة ثابتة لهما في جسم wrapper نفسه.

### 11.2 مؤشرات أن النموذج واجهة إعداد/اتصال

تحتوي الفئة نفسها على:
- دوال تحقق من عنوان IP باستخدام `IPAddress.TryParse`.
- دوال تقرأ `RadioButton.Checked` و`CheckBox.Checked` و`Control.Text`.
- دوال تشغيل `BackgroundWorker` ومعالجة `DoWork` و`RunWorkerCompleted`.
- عناصر واجهة من نوع `Label` و`TextBox` و`Button` و`TableLayoutPanel` و`CheckBox` و`RadioButton`.

هذا يثبت أن اتصال TCP موجود داخل نموذج واجهة تفاعلي ويحتمل أن يكون نموذج إعداد/اتصال. لا يثبت وحده أن الوجهة MikroTik أو أن البروتوكول RouterOS API.

### 11.3 ما زال غير محسوم

- لم يُكشف بعد أي حقل بعينه يمثل عنوان الراوتر أو المنفذ أو اسم المستخدم أو كلمة المرور.
- لم يُكشف أي `NetworkStream.Write/Read` مرتبط بعملية الاتصال.
- لم تُستخرج صيغة المصادقة أو كلمات RouterOS أو حدود الرسائل.
- ملف `network-callers.txt` أصبح يسجل دوال API المباشرة مع MethodDef tokens، لكنه لا يحتوي روابط `DEPTH=` إلى مستدعياتها. لذلك لا نعتبره call graph مكتملًا.
- ملف `form-delegate-map.txt` يكشف نقاط ربط BackgroundWorker/Timer لكنه لم يربط delegates بأسماء handlers؛ الربط القريب عبر ldftn غير ظاهر في هذه المقاطع.

### 11.4 قرار التحليل التالي

أضيف استخراج IL كاملًا ومنقحًا للنماذج التي تحتوي استدعاءات TCP أو OleDb، مع حقولها وMethodDef tokens، مع إخفاء النصوص غير المعروفة بواسطة SHA-256 وإخفاء النصوص الحساسة. الهدف هو كشف كيف تنتقل القيم من عناصر الواجهة إلى دوال الاتصال، وكيف تُكتب وتُقرأ بيانات الشبكة، دون تشغيل التطبيق أو تجاوز الحماية.
